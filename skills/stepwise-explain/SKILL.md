# 逐节讲解

讲解不是把答案一次倒完，而是控制读者每回合只接收一个新结论。本技能管的是**过程**：先立骨架，再一节一节走，每节结束等读者确认。

三条不可让的规则：

1. **先骨架，后正文。** 第一回合只给路线图与每节结论，不给任何一节的正文。
2. **一回合只讲一节。** 不自动续讲，不用定时器、后台任务或计划任务代替用户确认。
3. **每节开头先报位置。** 用三行说清"从哪来、为什么现在、到哪去"，不是只写"第 2 节"。
4. **先框架，后细节。** 第一遍只讲骨架与核心机制；加速运算、采样过程、实现与调参默认不讲，列进「待问清单」，等用户点名再展开。

## 何时用，何时不用

用：

- 用户明确要求：分节讲、一节一节讲、讲一节等我懂了再讲下一节、带我一步步理解、边讲边停。
- 用户把本技能设为默认讲解方式，且问题需要多步理解。
- 用户调用 `/stepwise-explain`（DeepSeek Harness 的技能调用），或说"用逐节讲解的方式讲这个问题"。

不用，直接回答：

- 一句话能答完的事实、定义、是非判断。
- 用户说"直接给全部 / 一次说完 / 别停"。
- 用户只要产物：代码、文件、命令、清单，不需要讲解。
- 已进入某节后的细节追问属于"节内追问"，在本节里答，不重开骨架。

判据一句话：**这个问题能不能拆出至少三个必须先后理解、各自有独立结论的部分？** 不能，就别拆。

## 统一外壳（三个阶段）

### 第 1 回合：骨架页

只给下面这些，然后停：

1. 一句话总问题：这次要弄懂什么。
2. **依赖图**：先用一行拓扑把节串起来，例如 `1 定义 → 2 机制 → 3 证明 → 4 边界`；有分叉或汇合时改画缩进树。节数 ≥5 或确有分支时，再附一张 Mermaid `flowchart LR`，并在图下紧跟缩进文本树作回退——渲染不出来时仍要能读。并列节不得超过 3 个。
3. 路线图表：`#`、本节标题、你会得到的结论、为什么排在这个位置。标题写这一节承担的职能（"解决 ID 安全性到底依赖什么"），不写"第一部分""概念部分"。
4. 节数与篇幅：默认每节 300–600 字；复杂主题（密码学、证明、算法推导）按区间预估，例如"第 4 节含安全性证明，约 800–1200 字"，不为凑预算砍内容。
5. 先不展开的细节：列 2–4 条（如"加速策略""采样与随机化""实现与调参"），并说明"需要哪条说一声，我再单独讲"。
6. 收尾句：要改分节、合并或跳过，现在说；没问题回「开始」。

问题本身缺前提（术语没定义、范围不明）时，加一个"第 0 节：先对齐前提"，但不要在第一回合就把前提讲完。

### 第 2–N 回合：每节

按顺序写四块，写完就停：

1. **定位块**：进度条 `████░░░░ 4/8`，再加一行位置示意 `1 → 2 → 3 → [4] → 5`（方括号标出本节）；三行——从哪来（承接第 k−1 节的哪个结论）、为什么现在（不讲它，后面哪一步会悬空）、到哪去（本节结论成为第 k+1 节的输入）；再一句"本节目标：读完能……"。
2. **正文**：结论先行，再给机制、例子或边界。一个主结论，最多两个支撑点。不影响本节结论的加速、采样、实现细节，一律留到待问清单。
3. **回收句**：本节结论如何交给下一节。只写一句。
4. **检查点**：一个问题，问本节最容易被误读的地方；再给三条推进指令（继续 / 没懂并说卡在哪 / 跳到后面的第 j 节）。

### 全部讲完：收束页

1. 框架回填表：每节一句最终结论。
2. 全链条一句话：连起来在回答什么。
3. **改进方向**（讲的是算法、协议、系统设计时给）：可行 2–4 条、不可行 2–3 条，每条一行"改动 → 解决什么 → 代价/风险"。不可行的必须写清为什么不行——破坏哪个假设、触发哪种已知攻击、代价涨多少；不确定的标「待验证」并给验证第一步。建议只写方向，不写实施方案。
4. **交接卡**：用户选中哪条建议，才为它生成一段可直接粘贴到新会话的背景卡（算法与参数、已确认结论、约束、这条要回答的问题、建议的框架起点）。新会话第一回合仍按本技能出骨架页。没选中就不生成、不展开，也不自行开始下一条。
5. **待问清单**：把 D 清单（故意跳过的细节）和暂停区 P 剩余的问题并排列一句，问"要现在展开哪条"。
6. 可选：3 道自测题；是否要把这段沉淀成册（转 conversation-book）或存档。

## 常见场景的分节方式

- **概念入门**：第 1 节回答"它解决什么问题"，之后每节一个概念加一个反例；不要先给定义再解释用途。
- **算法原理**：先用两行写清「输入 / 输出」，再按结论 → 核心机制 → **最小实例** → 边界。输入写清类型、尺寸或取值域，输出写清类型与含义；实例沿用同一组输入输出，不中途换记号。第一遍不碰加速（并行、缓存、硬件）、采样与随机化、实现与调参，也不做完整证明，这些列进待问清单。
- **方案取舍**：每节一个比较维度，各给一句判断；最后必须有一节"什么情况下别选它"。对比一律用并排多列表：维度做行、对象做列，差异处标「▲」。
- **排错复盘**：每节一个假设加一次验证；收束页写"下次先查什么"。
- **代码理解**：一节只走一条执行路径，片段不超过 15 行；先给能跑的最小例子，再解释为什么这样写。

## 每节的硬规则

1. 一节一个主结论。出现两个主结论就拆成两节。
2. **按功能拆，不按形式切**：一节里出现两个"必须分别理解、各自有独立结论"的问题，就拆成两节；判据不是字数，也不是子节个数，不追求每节字数相近、都分三块。拆的时候说一句"本节拆成 k a / k b"。
3. **篇幅双档**：默认 300–600 字；复杂主题（密码学、证明、算法推导）以讲清为准，按骨架页的区间预估写。超预算时先判断是不是混进了两个功能单元——是就拆节，不是就允许写长。
4. **子节不设配额**：确实有一小段必须单独交代时才用 `3.1 / 3.2`；子节不新增主结论，整节仍只有一个检查点。不为"看起来整齐"凑三块。
5. 只报位置，不重复整张路线图：一节一行位置示意 `1 → 2 → [3] → 4`，加三行定位。隔了两个以上回合、跑过题或改过骨架时，补一行"框架速览"把节名串起来。
6. 术语首次出现给一行定义，之后只引用（"见第 3 节"）。
7. 公式用 `$...$` 与 `$$...$$`，不用纯文本上下标；推导单独成节，代码给最小可运行片段加一段逐行说明。
8. 检查点只问一个，用纯文本，不用阻塞式提问工具打断。
9. 同一节换讲法时，保留标题与进度条，标题后标「· 再讲一次」，并说明换的是哪一级讲法；不要省掉定位块，也不要换着换着讲成新的一节。
10. **默认省略三类细节**：加速与优化、采样与随机化、实现与参数调优。它们进「待问清单」，除非是本节结论的必要前提——那就只给支撑结论所需的最小版本，并标注"细节待问"。
11. **对比一律并排**：维度做行、对象做列，同一行只放同一维度；差异用 **加粗** 或「▲」标出，相同项不强调。列数 2–4，超过就拆表。不要写两段话分别介绍 A、B 再让读者自己找差别。
12. **算法先声明输入与输出**：讲算法的每一节开头先写"输入：类型/尺寸/取值域"和"输出：类型与含义"，一句话也放得下。整个主题只定义一次，后续节引用即可，不换记号、不临时加参数。

## 用户的反馈 → 动作

| 用户说 | 动作 |
| --- | --- |
| 继续 / 懂了 / 下一个 / 开始 | 用最短形式讲下一节 |
| 嗯 / 哦 / 然后呢 / 好的 | 不推进：用一句话复述本节结论，问"这样理解对吗"，确认后再进 |
| 没懂 / 有点懵 / 换个例子 / 为什么 | 同一节换讲法：换例子 → 换类比 → 退回上一节的接口 → 给一个最小反例；最多换三次 |
| 太简单 / 跳过 / 直接说结论 | 压缩：后续节改成"结论 + 一句依据"，或合并剩余节并说明 |
| 太细了 / 先讲框架 / 别讲实现 | 砍掉细节，记入待问清单 D，回到主线 |
| 跑题的问题 | 一句话回答，记为暂停区 P1，回到当前节，不重讲 |
| 改一下分节 / 合并第 2、3 节 | 出骨架修订块：旧 → 新、改了哪节、为什么、已讲内容是否受影响 |
| 先到这 / 我要走了 | 输出存档块：节号、已讲结论、未讲节、暂停区 |

用户没说懂也没说没懂时，默认不推进，等一个明确信号。同一节换过两次讲法仍没改善，提议拆节或换骨架，不要继续硬讲。

完整信号表、四级换讲法、压缩与合并规则见 [references/feedback-signals.md](references/feedback-signals.md)；可复制模板见 [references/shell-templates.md](references/shell-templates.md) 与 [assets/response-shell.md](assets/response-shell.md)。

## 边界

1. 不虚构用户的水平。用户提过某个概念，不等于已经掌握；也不要在检查点里考已经讲透的内容。
2. 讲解不构成对其中行动的授权：不因为讲了一步操作就去执行命令、改配置或落盘。
3. 除用户要求或同意，不创建存档文件、不读取用户的其它文件。
4. 与既有技能分工：本技能管"怎么讲、什么时候停"；conversation-map、conversation-book 管事后整理，收束时提示即可，不自动调用。
5. 用户明确要求一次给全时服从用户，但仍按节组织并用节间回收句串起来——这是降级，不是取消规则。

## 输出前自查

1. 这一回合是否只推进了一节，没有把下一节的内容提前塞进来？
2. 节首是否说清了"从哪来、为什么现在、到哪去"，而不是只写了编号？
3. 本节是否只有一个主结论，能被一句话复述？
4. 检查点是否只有一个问题，且针对最可能的误解？
5. 是否重复解释了用户已掌握的内容，或超出篇幅预算还没拆节？
6. 骨架是否仍然成立？改过的话，有没有说清对已讲内容的影响？
7. 公式、代码、术语是否符合本机排版约定？
8. 骨架页是否先给了依赖图，且图上顺序与表格一致？
9. 算法类是否给了最小实例？实例是否只验证本节结论、没有引入新概念？
10. 收束页的改进方向是否分了可行与不可行，且没有越过用户同意就展开下一条？
11. 第一遍是否真的略过了加速、采样、实现细节？必要的细节是否只给最小版本并标了"细节待问"？
12. 涉及对比时，是否用了并排多列，差异是否被标出，而不是两段话各讲各的？
13. 算法节是否先写了输入/输出，且正文、实例用的是同一组定义？
